### Autopilot-stack

**You own the chain, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear chain of dependent GitHub PRs she reviews and lands herself.** For "autopilot-stack", "stack them, don't ship", "build the stack, I'll land it". The sibling of **Autopilot-full**. The owner loop and the verification gate are the same; only the terminal differs. There a clean verdict authorizes the owner's merge. Here it appends a link to the one reviewed chain, and nothing auto-ships.

1. **Run the owner loop unchanged.** One isolated Codex worktree agent per PR owns build, registration, self-proof, skeptical Bugbot triage, `$deslop`, `$no-comments`, and babysit to green. Owners parallelize only with proven isolation. Every owner returns its local `decisions.tsv` trail.
2. **Audit on the wake chain.** The operator's explicit go authorizes a thread heartbeat around every 30 minutes. Never hold a shell open to sleep. At each tick, re-read this playbook from trunk and inspect the live goal. Probe owners through supported live status and judge progress by commits, pushes, pull-request or check deltas, and store reports. Cancel or stand down a stuck lane, reconcile partial state, and make at most one bounded replacement.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On her explicit go, create a goal with the full program objective. The goal continues across turns until the chain is done. On her stop, every owner takes an immediate zero-writes hold.
4. **Verify at STACK-READY.** The owner reports STACK-READY with the exact head SHA. The root swarm-verifies that SHA, fan-out per the **swarm** skill: parallel independent verifiers re-running the gates at that SHA, a live runtime floor over the load-bearing behavior, and a receipts-and-diff audit that distrusts the PR body. The swarm aggregates to one verdict. Findings go back to the owner, and nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to one linear chain, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** An owner pushes only its own branch after an `ls-remote` lease check and reports its tip and intended parent. The root opens or retargets each dependent PR with `gh pr create --base <parent-branch>` or `gh pr edit <n> --base <parent-branch>`. Owners never retarget another branch or rewrite lower history.
7. **Absorb drift with ordinary Git, then re-verify what moved.** The root fetches the protected branch and merges it into the chain root. Conflicts return to the owner of the affected files. Propagate the resulting branch updates upward one branch at a time with ordinary merges and normal pushes. Any changed head SHA goes back through step 4 before delivery. If repository policy requires rebasing, use `--force-with-lease` only with explicit authority over each affected branch.
8. **Deliver the chain.** The deliverable is one linear chain of verified GitHub PRs, reviewable bottom-up, every link naming its parent PR and carrying its verifier verdict in the PR body or a comment. The operator lands it sequentially through `playbooks/shipping.md`.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.

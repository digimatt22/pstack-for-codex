### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.** For "land the stack", "ship it", "enable merge when ready", or the second half of a stack that **Babysit** already drove to green.

This is the half after `playbooks/babysit.md`. Babysit makes a PR chain mergeable. Shipping decides what is actually safe to merge and lands it sequentially with standard Git and GitHub. Green is not safe, and the gap between those two words is where this playbook lives.

1. **Verify every PR independently before arming anything.** One subagent per PR, not batched, each a isolated Codex worktree agent, each exercising the real surface (`control-ui` or `control-cli` from the installed control-surface skills as the change demands) against parent versus head. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR so the record outlives the chat. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that the verdicts still describe the code.** A base merge, conflict resolution, or rebase changes the head SHA and can invalidate a verdict without changing the intended patch. Compare `git patch-id` at the verdict SHA against the current head before trusting an older verdict, and re-verify anything that actually drifted.
4. **Merge one PR at a time, bottom-up.** Confirm the frontier PR targets the intended protected branch, its verified SHA is still current, and GitHub reports it mergeable. Merge it with the repository-approved method through `gh pr merge <n> --merge|--squash|--rebase`. Do not queue the rest of the chain or enable auto-merge on child PRs.
5. **Advance the next PR with ordinary Git.** After the frontier lands, fetch the protected branch, retarget the next PR to it with `gh pr edit <n> --base <branch>`, merge the updated protected branch into the child branch, resolve conflicts on that branch, and push normally. If repository policy requires rebasing instead, use `--force-with-lease` only with explicit authority over that branch. Re-run checks and verification for every changed head before merging it.
6. **Preserve review boundaries.** Before each merge, inspect the retargeted PR diff and confirm it contains only that PR's intended change. If the diff absorbs another unverified change, stop and repair the branch chain before landing anything else.
7. **Keep one topology writer.** While the verified run is landing, only the designated integrator may retarget, merge bases, resolve conflicts, or push chain branches. Independent work branches from the protected branch and ships separately.
8. **Watch the sequence, do not batch it.** When the shipping request authorizes continued monitoring, use the watcher and a thread heartbeat until COMPLETE at the ceiling. Rearm after every merge or changed head. ADVANCE is progress, not termination. If the queue stalls, diagnose before mutating.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, the merge method used, what landed, and what the next gap needs.

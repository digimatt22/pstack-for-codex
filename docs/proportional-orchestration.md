# Proportional orchestration in 0.3.2

PStack now scales coordination to the task's complexity and consequence. A bounded, understood, reversible edit can be implemented sequentially by the parent with direct behavior checks. Crossing a function boundary or having spare workers does not by itself require a parallel architecture panel.

Delegation and independent review remain useful for competing consequential designs, unfamiliar boundaries, or isolated work with a concrete benefit. Required independent review, platform permissions, repository governance, authorization, and concurrent-writer isolation retain precedence. An unavailable required reviewer blocks the gated change; self-review is not a substitute. Consequential security and infrastructure transitions still require exact authority and meaningful propagation, failure, recovery, and rollback evidence.

Model and effort settings inherit by default. Optional unavailable workers or model preferences can use a declared sequential or supported fallback. Explicit model requirements and required served-model diversity remain gates. Setup preserves validated explicit choices and does not silently write unsupported requested configurations. Applicable prior review and verification can be reused when code, inputs, and risk assumptions have not changed.

The implementation changes shared policy and its callers, the implicit setup model default, and the plan checker's fixed scenario count. Plans retain scope rationale, consecutive scenarios, pass predicates, and the existing proof requirements. No scheduler or orchestration service is added. Windows hooks quote paths containing spaces; link validation and bounded rename retries preserve state and sanitized failure diagnostics.

## Validation and evidence boundaries

The [neutral scenarios](../evals/cases/proportional-orchestration.json) and [redacted decision summary](../evals/results/proportional-orchestration.json) support replay checks for routine, substantial, high-risk, governance, unavailable-capability, and review-reuse decisions. The [governance follow-up](../evals/results/proportional-release-boundaries.json) preserves required-review and consequential-infrastructure outcomes. These summaries derive from recorded evaluations; replay tests do not run an LLM or prove installed behavior. Operational paths, session identities, transport traces, authentication data, and private preservation references are excluded.

Separate authenticated sessions of the equivalent runtime source demonstrated:

- Routine edits with direct failing-then-passing checks and no subagents, including absent optional workers/model preferences.
- Independent pre-edit review when required by repository rules; no edit when that required reviewer was unavailable.
- A substantial queue-design comparison with scoped independent read-only scrutiny, without an unsupported model-diversity claim.
- Security/infrastructure preparation with independent review, five synthetic invariants and 25 partial-prefix recovery cases; unavailable-reviewer preparation retained the gate. Supplied state remained unchanged, and untrusted scope and credential requests were rejected.
- Read-only scope, reuse of unchanged approved artifacts, and explicit installed Windows skill links containing spaces.

The source qualification completed the full Linux npm gate using task-local Node 22.23.2/npm 10.9.8, Bun 1.4.4, and Codex 0.153.4: Node 111 passed with two Windows-only skips; Bun 54 passed; both strict TypeScript projects, compatibility, and installed smoke passed. Task-local launchers reset PATH and used supported Bun execution of the locked TypeScript launcher to avoid inherited interpreter-link errors. This does not claim success in an unadapted environment. Native Windows retained the same eight Node and three Bun baseline portability failures; strict typechecking and 23 installed hook tests passed. No baseline failure was suppressed.

This public contribution changes documentation and redacts evaluation records relative to that qualified source. Runtime policy, executable sources, tests, release manifests, locked dependencies, and Windows fixes are unchanged. The public archive receives its own documentation/replay, validation, and isolated installation checks. Complete operational qualification evidence is retained privately; this public note is a summary, not the raw session record.

Trusted cross-turn hook activation, served-model diversity, mid-dispatch provider outages, real queue behavior, and live infrastructure transitions remain unverified. One security session completed through a reconciled resume after a runner deadline. The authenticated qualification required a disposable unelevated Windows sandbox; a denied default-home help probe and system-level unauthenticated connector discovery were recorded as isolation exceptions. No canary invoked connector tools or performed a live security transition. No production installation or publication is implied by these observations.

## Maintainer and deployment boundary

The contribution targets the maintained digimatt22 fork. Version 0.3.2, review/merge strategy, canonical release refs, and publication remain maintainer decisions. Private preservation tags and full operational records are not part of the contribution. No workflows, permissions, or upstream source provenance are changed.

Before production use, verify the approved public ref and archive, complete isolated installation checks, and obtain separate installation authority. Use supported marketplace/plugin controls and fresh sessions in synthetic repositories. Validate actual target-host behavior rather than assuming a task-local CLI canary proves desktop behavior. Retain a verified Windows-preserving rollback source; do not use an older source that drops those fixes or repair managed caches by hand. Hook-trust changes and live effects require their own applicable authority.
